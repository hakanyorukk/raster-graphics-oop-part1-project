Chapter 1. The Lead

1.1. Description and idea of the project

This project is a console-based raster (bitmap) image editor written in Java that works with the three plain Netpbm image formats: PBM (black-and-white), PGM (grayscale) and PPM (colour). The user interacts with the program through a command-line interface, loading one or more images into a numbered session, queueing transformations such as grayscale, negative, monochrome and 90° rotation, and finally writing the results back to disk. Several independent sessions can exist at the same time, and the user can switch between them. The central idea is that transformations are deferred: they are only physically applied to the pixels when the user saves, which keeps the original data intact until the last possible moment.

1.2. Purpose and objectives of the development

The purpose of the project is to build a correct, robust and cleanly structured image editor that demonstrates the core principles of object-oriented programming. The concrete objectives are:

  • To read and write valid Netpbm files (magic numbers P1, P2, P3) without corrupting them.
  • To support the full command set required by the assignment: load, add, close, save, saveas, help, exit, grayscale, monochrome, negative, rotate, undo, session info, switch and collage.
  • To manage multiple images and multiple sessions with deferred (pending) transformations.
  • To apply object-oriented design (inheritance, polymorphism, interfaces and design patterns) so that the program is easy to extend and to defend.
  • To fail gracefully — never crash on invalid input, but report a clear message instead.

Chapter 2. Overview of the subject area

2.1. Basic definitions, concepts and algorithms

A raster (bitmap) image is a rectangular grid of pixels. This project works with the Netpbm family of formats, which store the pixel grid as plain ASCII text. Every file begins with a two-character magic number that identifies the format, followed by the width, the height, an optional maximum colour value, and then the pixel data separated by whitespace:

FormatMagicMeaningPixelMax value
PBMP1Portable Bitmap (black & white)one value, 0 or 1fixed at 1
PGMP2Portable Graymap (grayscale)one value, 0..maxe.g. 255
PPMP3Portable Pixmap (colour)three values R G B, each 0..maxe.g. 255

Table 1. The three supported Netpbm formats.

The transformations rely on the following algorithms:

  • Grayscale — for a colour image, every pixel is replaced by the average of its channels, gray = (R + G + B) / 3, written back into all three channels so the image stays a valid PPM. Grayscale has no effect on PBM/PGM images, which already contain no colour.
  • Negative — every value v is replaced by max - v (for PBM, 1 - v), inverting the image.
  • Monochrome — each pixel is compared with a threshold of max / 2; values below it become 0 and the rest become max, leaving only two tones.
  • Rotation (90°) — performed by remapping pixel coordinates and swapping the width and height (see section 4.2).
  • Collage — two images of the same format and size are copied into a larger array, side by side (horizontal) or stacked (vertical).

2.2. Defining problems and complexity of the task

The main difficulties of the task are:

  • Three different formats with different pixel representations (one channel for PBM/PGM, three for PPM) and a different header (PBM has no max-value line). The code must treat them uniformly without scattering format checks everywhere.
  • Deferred transformations — operations must be remembered and applied only at save time, which means the program keeps a queue of pending operations per session.
  • Multiple sessions — several independent working contexts must coexist, each with its own images and its own pending operations.
  • Robust I/O — the program must produce files that are still valid Netpbm and must not crash on a missing or malformed file.

2.3. Approaches and methods for solving the problems

The problems above are solved with object-oriented techniques rather than long conditional blocks:

  • Polymorphic image hierarchy — each format is its own class, so format-specific behaviour is selected by polymorphism instead of if (format == "P3") checks.
  • Command design pattern — each user command is a separate class, so the main loop does not contain a large switch statement.
  • Strategy pattern — each transformation is an object that can be stored in a list and applied later, which directly supports the deferred-transformation and undo requirements.
  • Factory — a single place (the reader) decides which image subclass to create from the magic number.

Chapter 4. Implementation and testing

4.1. Class implementation

The image hierarchy

The abstract class Image holds only the data common to all formats (name, width, height) and declares the operations every image must support. Each concrete format provides its own pixel storage and its own implementation, which removes all format.equals(...) branching:

public abstract class Image {
    protected String name;
    protected int width, height;

    public abstract String magicNumber();   // "P1" / "P2" / "P3"
    public abstract Image negative();
    public abstract Image rotateLeft();
    public abstract Image rotateRight();
    public abstract Image grayscale();
    public abstract Image monochrome();
    public abstract Image collage(Image other, CollageDirection dir, String name);
    public abstract String toNetpbm();       // serialise to valid Netpbm text
}

Because PBM and PGM both store a single value per pixel in an int[][] grid, their shared logic (negative, rotation, collage, serialisation) lives once in an intermediate abstract class, SingleChannelImage. PPMImage stores three channels in an int[][][] grid and overrides the operations itself. A key design decision is that grayscale() on a PPM keeps the image a PPM (it sets R = G = B), so the saved file stays valid and its extension still matches its contents.

The Command pattern

Every user command is a class implementing a small interface:

public interface Command {
    void execute(String[] args, AppContext ctx);
}

Commands that require a loaded session extend the abstract class ActiveSessionCommand, which performs the "is a session loaded?" check once (the Template Method pattern) and only then calls the subclass:

public abstract class ActiveSessionCommand implements Command {
    public final void execute(String[] args, AppContext ctx) {
        if (ctx.sessions().getCurrentSession() == null) {
            System.out.println("No active session. Use 'load <file>' to start one.");
            return;
        }
        run(args, ctx);
    }
    protected abstract void run(String[] args, AppContext ctx);
}

The CommandRegistry maps command names to objects, and the Editor loop simply looks up the object and runs it — there is no large switch statement. AppContext is a small interface exposing only the services a command may use (the session manager, the reader and the writer), so commands depend on this contract rather than on the whole application class. Args is a utility class with the shared validations (argument count, valid file extension).

Sessions

A Session owns its images and a queue of pending transformations. The transformations are applied only on save:

public void applyPending() {
    for (Transformation t : transformations) {
        for (int i = 0; i < images.size(); i++) {
            images.set(i, t.apply(images.get(i)));
        }
    }
    transformations.clear();
}

SessionManager keeps all sessions in a map keyed by id, tracks the current session and hands out consecutive ids.

Input / output

ImageReader opens a file, reads the magic number and is the single place that decides which subclass to build (a Factory):

String magic = scanner.next();
return switch (magic) {
    case "P1" -> readPbm(path, scanner);
    case "P2" -> readPgm(path, scanner);
    case "P3" -> readPpm(path, scanner);
    default  -> throw new InvalidImageName("Unsupported format " + magic);
};

ImageWriter only deals with the filesystem; the textual form of each format is produced by the image itself via toNetpbm().

4.2. Algorithms and optimisations

90° rotation. A rotation is done by allocating a new grid with swapped dimensions and copying each pixel to its rotated position. For a counter-clockwise (left) rotation the mapping is new[width-1-c][r] = old[r][c]; for clockwise (right) it is new[c][height-1-r] = old[r][c]. After copying, the width and height are swapped. This is an O(width × height) operation, which is optimal because every pixel must be touched once.

public Image rotateLeft() {
    int[][] rotated = new int[width][height];
    for (int r = 0; r < height; r++)
        for (int c = 0; c < width; c++)
            rotated[width - 1 - c][r] = pixels[r][c];
    pixels = rotated;
    swapDimensions();
    return this;
}

Grayscale / negative / monochrome are all single passes over the pixel grid (O(width × height)), each touching every pixel once.

Deferred application. Instead of transforming the pixels immediately, each operation is stored as a Transformation object in the session's queue and applied only at save time. This makes undo trivial (remove the last element of the queue) and avoids repeatedly rewriting the pixel arrays.

Chapter 5. Conclusion

5.1. Summary of the implemented objectives

All the objectives set in section 1.2 were achieved. The program reads and writes valid PBM, PGM and PPM files, supports the full required command set, manages multiple images and sessions with deferred transformations, and never crashes on invalid input. The code was restructured from two large classes into seven focused packages, demonstrating inheritance, polymorphism, interfaces and several design patterns (Command, Template Method, Strategy, Factory).

5.2. Directions for future development and improvement

  • Support the binary Netpbm variants (P4, P5, P6) in addition to the plain ASCII ones, for smaller files.
  • Make a freshly add-ed image ignore transformations that were queued before it was added, by tracking a per-image starting index.
  • Support file paths that contain spaces (quoted arguments).
  • Use a weighted luminance formula (0.299R + 0.587G + 0.114B) for a more perceptually accurate grayscale.
  • Add more transformations (crop, scale, flip, brightness/contrast).
